# Profiling `mafft-rs`

## Build

We expose a `profiling` Cargo profile (`Cargo.toml`) that inherits from
`release` but keeps DWARF debug info so profilers show symbol names:

```sh
cargo build --profile profiling --bin mafft-rs
# binary: ./target/profiling/mafft-rs
```

## Tools

### macOS `sample` (recommended — built in, no install, no sudo)

Best for ad-hoc profiling on macOS. Spawns mafft-rs in the background,
samples it for N seconds, then writes a symbolicated call-graph text
report.

```sh
# spawn the workload in the background
./target/profiling/mafft-rs --maxiterate 50 /tmp/sample_108.fa > /dev/null &
RPID=$!
sleep 0.1                          # let argparse + file read finish
sample $RPID 8 -file /tmp/sample.txt
wait $RPID

head -50 /tmp/sample.txt           # call graph
grep -A2 "profile_align" /tmp/sample.txt | head -40   # zoom on a hot func
```

Extract top function leaves from the symbolicated graph (rough total
samples per function, including ancestors — useful for finding hot
modules quickly):

```sh
grep -oE '[0-9]+ [a-zA-Z_:$]+::[a-zA-Z_$:.]+::h[0-9a-f]+' /tmp/sample.txt | \
  awk '{cnt=$1; $1=""; sub(/^ /,""); name=$0; sub(/::h[0-9a-f]+$/, "", name); a[name]+=cnt} \
       END {for(n in a) print a[n], n}' | sort -rn | head -25
```

The bottom of `/tmp/sample.txt` also has a "self time" leaf summary
that's more accurate than the ancestor-rolled top counts.

### `samply` (installs without sudo; interactive UI if desired)

```sh
cargo install samply

# Save to file only (no browser) — JSON profile, unsymbolicated by default.
samply record --no-open --save-only -o /tmp/prof.json --rate 997 \
    --iteration-count 10 -- \
    ./target/profiling/mafft-rs --maxiterate 50 /tmp/sample_108.fa

# Open the interactive Firefox profiler UI (auto-symbolicates on load).
samply load /tmp/prof.json
```

samply on macOS can't spawn through `/bin/bash` wrappers (system
binaries block `DYLD_INSERT_LIBRARIES`); always invoke a directly-cargo-
built binary. For loops, use `--iteration-count N` rather than a shell
loop.

### `cargo flamegraph` (needs sudo on macOS)

Standard Rust convention but requires `dtrace` (sudo per run). Not used
in the autonomous-profiling recipe above; mentioned for completeness if
you want SVG output to share in a PR:

```sh
cargo install flamegraph
sudo cargo flamegraph --profile profiling --bin mafft-rs -- \
    --maxiterate 50 /tmp/sample_108.fa
# writes flamegraph.svg in the working directory
```

overhead, hiding hot loops behind argparse + file I/O. For profiler
runs use a longer-running input:

  sample with 5% per-sequence shuffle perturbation). Generated by

  re-create on demand with:

  ```sh
  python3 -c "
  import random; random.seed(42)
  seqs = []

  with open('mafft-upstream/test/sample') as f:
      for line in f:
          if line.startswith('>'):
              if cur_name: seqs.append((cur_name, ''.join(cur_seq)))

              cur_seq.append(line.strip())

  with open('/tmp/sample_108.fa', 'w') as f:
      for rep in range(3):

              chars = list(seq)
              for _ in range(max(1, len(seq) // 20)):

                  chars[a], chars[b] = chars[b], chars[a]
              f.write(f'>r{rep}_s{i}_{name}\n{\"\".join(chars)}\n')

  ```

## Profile snapshot (2026-05-18)

Command: `sample` on `mafft-rs --maxiterate 50 /tmp/sample_108.fa`
(one-shot, ~1.4s run, ~1300 samples on the main thread).

| Self-time samples | Function | % of main thread |
|-------------------|----------|------------------|
| 509 | `mafft_align::profile::profile_align_imp_with_boundary` | **55%** |
| 97 | `mafft_core::refinement::compute_split_score` | 11% |
| 89 | `mafft_align::profile::Profile::from_aligned` | 10% |
| 26 | `mafft_align::profile::Profile::match_score` | 3% |
| remaining 22% | rayon scheduling, allocation, traversal | — |

**Interpretation**: the 18% Rust-vs-C deficit on `--maxiterate 50`
(108-seq input) is dominated by the inner DP cell loop in
`profile_align_imp_with_boundary`. Within that function, ~86% of its
self time (501 of 582 samples, including a few ancestor-rolled
allocator frames) is in the cell-update inner loop; the remaining 14%
is `Vec` allocation for `ijp`, `h`, `cpmx2_sparse`, and per-row
buffers.

The DP body has FMA throughout (`§4` BL50 close, `§B.2` audit, `§C.2.1`
profile-build fusion) and matches C's inner loop arithmetic 1-for-1 on
the same platform (since 2026-09-06 through `mafft_types::fp::fmadd`,
fused on aarch64 and not on x86-64, mirroring the reference C build —
see `docs/architecture/byte-identity.md`) — but C's `A__align` re-uses
`static TLS` buffers across calls (the BB20027 deep-dive in
`balibase_parity_run.md` records the static-state investigation) while,
at the time of this snapshot, our Rust allocated fresh per call. The
remaining gap was thought to be allocator-driven, not arithmetic.

## Closing the FFT-NS-i gap — three candidate paths

Ordered by effort:smallest to largest:

1. **Pre-allocated buffer arena threaded through `profile_align_imp_*`**
   — replace the per-call `vec![]` of `ijp` (n × m i32), `h` (n × m
   f64), `cpmx2_sparse` (m × Vec<(usize, f64)>), and row buffers with
   a `&mut DpScratch` parameter that callers can hand in. The
   refinement loop creates one scratch per thread and reuses it across
   all branches. Expected impact: closes the ~14% allocation overhead
   inside `profile_align_imp_with_boundary` (~70 samples), worth
   roughly 7-10% of the FFT-NS-i runtime.

2. **`compute_split_score` branchless inner** — current
   `pairwise_score` (`refinement.rs:1093`) has 3-4 branches per
   residue (gap-gap / gap-a / gap-b / match) that prevent LLVM
   auto-vectorization. Reformulating as a mask-multiply + a separate
   gap-run pass would let LLVM SIMD-ify the residue-residue path.
   Expected impact: ~5% of FFT-NS-i runtime.

3. **Anti-diagonal DP rewrite** (§C.2 original framing) — reorder the
   `profile_align_imp_with_boundary` cell update so adjacent cells in
   an anti-diagonal can be processed independently, then SIMD over
   anti-diagonals. Major undertaking — touches the warp DP, the
   gap-skip trackers (`mi`, `mj`), and the traceback ordering. Highest
   potential gain (could double DP throughput on a flat-landscape
   matrix), but ~1-2 days of work plus byte-equivalence regression
   risk.

The cumulative effect of (1) + (2) would likely close most of the
~18% gap with a few hours of work. (3) is reserved for a hypothetical
scenario where FFT-NS-i is a sustained bottleneck for users.

### Attempt log (2026-05-18)

- **(1) landed perf-neutral**: `h` / `ijp` are now pooled via
  `thread_local!` in `mafft-align/src/profile.rs`. Re-profile confirmed
  raw_vec growth samples inside `profile_align_imp_with_boundary`
  dropped from ~80 to ~20-30. Wall-clock impact on
  `--maxiterate 50 /tmp/sample_108.fa` (3 trials × 5 runs): pre-path-1
  Rust ≈ 6.77s vs post-path-1 Rust ≈ 6.74s — within measurement
  noise. macOS's malloc/free is already fast enough that the saved
  allocations weren't the bottleneck. Pooling kept anyway (cleaner
  code, mirrors C `A__align`'s `static TLS` buffer strategy).

- **(2) reverted**: the per-cell state-machine reformulation of
  `pairwise_score` failed 16 byte-identity tests because C's
  `while (seq1[k] == '-')` consume loop walks through both-gap
  positions (it only looks at seq1), while a naive per-cell
  reset-on-both-gap rule re-charges penalty when an A-gap-run is
  interrupted by a both-gap column. The minimum branchless form that
  matches C exactly is a 3-state machine (Neutral / AGapRun /
  BGapRun) — still branchy, no clean SIMD path. Reverted to the
  C-style while-loop with an explanatory comment.

Net: the remaining ~18% FFT-NS-i gap is dominated by the inner DP
cell update itself (456 of 922 main-thread samples post-path-1). Only
path (3) — anti-diagonal SIMD restructuring — would close it
meaningfully, and that's a multi-day project with regression risk on
the warp DP, gap-skip trackers, and traceback ordering. Currently
not worth pursuing without a sustained-bottleneck workload.

### Update (2026-09-06): flattened scratch buffers landed

The data-layout half of path (1) shipped with the issue #1 integration
(PR #2, extracted from Johan Henriksson's fork, mahogny/rust-MAFFT
0b3955d):

- `profile_align_imp_multimtx`: `h` / `ijp` are flat row-major
  `(n + 1) * (m + 1)` buffers (stride `m + 1`) from the existing
  thread-local pools instead of `Vec<Vec<_>>`; the sparse `cpmxpd` /
  `cpmxpdn` column profiles are one flat entry list plus a `len + 1`
  offsets table each; `match_calc_row_into` walks the scoring matrix
  j-outer / l-inner over contiguous rows; the boundary-init `bcarr`
  buffer is pooled instead of allocated twice per call.
- `local_align` (`L__align11`): a thread-local `LocalScratch` replaces
  seven allocations per call, `seq2` is mapped to alphabet indices once,
  the match score is added inside the DP cell (same operands, same
  order), and the j-loop body is the const-generic `local_dp_row::<HAS_ROW>`
  kernel.

Every multiply-add still goes through `mafft_types::fp::fmadd` with
unchanged operand order, so output is byte-identical (verified on the
36-seq sample across the default / `--maxiterate 1000` / L-, G-, E-INS-i /
`--bl 50` / `--parttree` runs and on the 120 × 1.4 kb DNA reproducer, and
the `fp-contract-none` build still gives x86-64's 738 columns on `--bl 50`).
Wall-clock medians of 5 interleaved runs, Apple M4, vs the previous
`mafft-rs`: `mtb_cds_120x1400 --retree 2 --maxiterate 2` 4.99 s → 4.62 s
(1.08×), sample `--localpair --maxiterate 1000` 0.85 s → 0.77 s (1.11×),
sample `--maxiterate 1000` 0.54 s → 0.48 s (1.14×), sample default
0.066 s → 0.055 s (1.21×).

So the "allocator-driven" reading above was partly right: the win came
from contiguity and fewer allocations, not from pooling alone. Path (2)
stays reverted (the 3-state gap-run machine is the minimum that matches
C) and path (3) stays open. `MAFFT_RS_REFINE_STATS=1` now prints per-call
refinement statistics (`cycles`, `visited`, `accepted`, exit reason) so
any future C-vs-Rust timing can first confirm both sides ran the same
refinement work.

## Scaling benchmark: n = 100 to 5000 (issue #22)

`benchmarks/scaling_corpus.py` builds the corpus and
`benchmarks/scaling.py` times C MAFFT (in-tree build), the `mafft-rs`
CLI and native `pymafft.align()` on it, interleaved, recording
wall-clock, peak RSS, output width and C-vs-Rust byte-identity per run.
Both scripts' docstrings have the details.

**Corpus.** Ten Pfam families as full-length UniProtKB sequences (query
`xref:pfam-<ID> AND fragment:false AND length:[50 TO 3000] AND
(reviewed:true OR existence:1)`, UniProt 2026_03) and RefSeq 16S rRNA
(BioProject PRJNA33175, NCBI E-utilities), each shuffled with a fixed
seed and cut into nested subsamples n = 100, 250, 500, 1000, plus 5000
for PF00069 / PF00005 and 2000 for 16S (PF00528 has 541 members, so it
stops at 500). The manifest (pool size, release, download date, length
min / median / max / total per subsample), the ordered accession lists
and `SHA256SUMS` are in `benchmarks/corpus/`; the FASTA files are
regenerated into `target/scaling_corpus/`:

```sh
benchmarks/scaling_corpus.py build    # fetch the committed accessions, check SHA256SUMS
benchmarks/scaling_corpus.py verify
```

**Grid.** FFT-NS-2, FFT-NS-i (`--maxiterate 1000`), L-INS-i
(`--localpair --maxiterate 1000`), `--parttree`, and G-INS-i
(`--globalpair --maxiterate 1000`) for n ≤ 250; n > 1000 only for
FFT-NS-2 and `--parttree`; `--thread 1` everywhere and `--thread 8` for
n ≥ 500 — 290 cells (`scaling.py run --list`). Cells run in increasing
n; a cell is skipped (with every larger n of the same set and mode) when
C's time projected from the previous n (quadratic; n^1.2 for
`--parttree`) exceeds `--budget` (3600 s), or C timed out there. Single
runs time out after 7200 s. `pymafft.align()` does not expose
`--parttree`, so those cells have no pymafft column.

**Running.** Prerequisites: `make -C mafft-upstream/core`,
`cargo build --release -p mafft-rs`, a `.venv` with
`maturin develop --release` of `crates/pymafft`. Then, on a quiet
machine:

```sh
benchmarks/scaling.py run --smoke        # one cell, seconds
benchmarks/scaling.py run --reps 3          # full sweep
benchmarks/scaling.py summarize benchmarks/results/scaling_darwin-arm64_<date>.tsv
```

Every run is cached under `target/scaling/<host>/` (host defaults to
`<os>-<arch>`, e.g. `darwin-arm64`, `linux-x86_64`), so an interrupted
sweep resumes where it stopped. Run it on each platform against that
platform's own C build; `scaling.py compare a.tsv b.tsv` then lists the
cells where the two C builds disagree with each other.

`benchmarks/results/scaling_smoke_2026-10-31.tsv` is the pipeline check
(n = 100, `--thread 1`, one replicate, every set): FFT-NS-2 is
byte-identical between C, `mafft-rs` and pymafft on all 11 sets;
`mafft-rs --parttree` panics on all 11 (`index out of bounds` in
`mafft_core::progressive::merge_step_cached`, from n ≈ 50 sequences up),
which has to be fixed before the `--parttree` column of the full run
means anything.

## High-throughput workload: thousands of small alignments (issue #23)

The full timed run is a day-long job on an idle machine; the step-by-step
hand-over is in [`benchmarks/htworkload/RUNBOOK.md`](benchmarks/htworkload/RUNBOOK.md).

The scaling benchmark measures one alignment at a time. Pipelines that
align *many* small clusters per run — panaroo / Roary aligning every gene
family of a pangenome, OrthoFinder-style orthogroup alignment, a
Snakemake / Nextflow rule per cluster — also pay a process spawn and a
FASTA round-trip per call. `benchmarks/htworkload_corpus.py` builds such
a workload and `benchmarks/htworkload.py` runs it end to end, several
ways, timing the whole run. Both docstrings have the details.

**Corpus.** Two sets of real clusters, member lists and per-cluster
SHA-256 in `benchmarks/htworkload/` (`manifest.tsv`, `clusters_dna.tsv`,
`orthogroups.txt`, `provenance.json`), FASTA regenerated into
`target/htworkload_corpus/`:

| Set | Clusters | Sequences | n min / median / mean / max | n = 2–9 / 10–49 / 50–100 | Length (median of cluster medians) |
|---|---:|---:|---|---|---:|
| DNA: *S. pneumoniae* gene families | 2695 | 56 658 | 2 / 29 / 21.0 / 100 | 776 / 1903 / 16 | 738 nt |
| Protein: OrthoDB v13 Saccharomycetaceae orthogroups | 1500 | 49 168 | 5 / 30.5 / 32.8 / 60 | 418 / 472 / 610 | 380 aa |

* DNA (primary): the CDS of 30 RefSeq complete genomes of
  *Streptococcus pneumoniae* (NCBI Datasets v2, drawn with a fixed seed
  from the 292 available), without pseudogenes, partial CDS and CDS
  < 90 nt, translated and clustered with MMseqs2 18
  (`easy-cluster --min-seq-id 0.7 -c 0.8 --cov-mode 0 --cluster-mode 0
  -s 7.5`: panaroo's 70 % family threshold); the families' DNA
  sequences, singletons dropped, five families above 100 members
  subsampled to 100. The `.fa` files in
  `crates/mafft-bin/tests/fixtures/panaroo_tiny_dna_clusters/` are the
  same kind of input.
* Protein (secondary): 1500 OrthoDB v13 groups with 5–60 genes at the
  Saccharomycetaceae level (60 species), drawn with a fixed seed from
  the 4074 of that size.

```sh
.venv/bin/python benchmarks/htworkload_corpus.py build    # needs no MMseqs2
.venv/bin/python benchmarks/htworkload_corpus.py verify
```

**What is run.** Every cluster is aligned with `--auto --adjustdirection
--thread 1 --nuc` (DNA, the panaroo command line of issue #1) or
`--auto --thread 1` (protein; without `--thread`, C takes its
single-threaded path but `mafft-rs` uses every core inside each
alignment), and with the same flags as `pymafft.align()` keywords. At
these sizes `--auto` picks L-INS-i for almost every cluster.

| `--impl` | What it is | What it measures |
|---|---|---|
| `snake-c` | `benchmarks/htworkload/Snakefile`, one job per cluster calling the in-tree C wrapper, `snakemake --cores W` | the baseline: a workflow manager around C MAFFT |
| `snake-rust` | the same Snakefile with `impl=rust` (`mafft-rs`) | the CLI swap alone |
| `loop-c`, `loop-rust` | a Python loop (thread pool of W) running the CLI as a subprocess per cluster | spawn + FASTA round-trip without the Snakemake scheduler: `snake-*` minus `loop-*` is scheduler overhead |
| `py-serial` | one Python process, `pymafft.align()` per cluster (W = 1) | no spawn, no temp files |
| `py-process` | `pymafft.align()` in a `ProcessPoolExecutor(W)` | the native API at W workers |
| `py-thread` | `pymafft.align()` in a `ThreadPoolExecutor(W)` | whether the released GIL lets threads match processes |

Each (molecule, impl, workers) cell is one whole run, measured as a
process tree: `/usr/bin/time -l` around the driver (around `snakemake`
for the Snakemake paths) gives wall-clock, user + system CPU over every
process of the run and the peak RSS of the largest single process;
`tree_rss_mb` is the peak summed RSS of the tree, sampled with `ps`
twice a second. Every output is then hashed and checked against the C
outputs of the same clusters (`identical_c`: byte-identical files for
the Rust CLI; same names and gapped sequences for pymafft, which does
not wrap lines).

**Running.** Prerequisites as for the scaling benchmark, plus
`snakemake` in the venv (`.venv/bin/pip install maturin biopython
snakemake`). On a quiet machine:

```sh
.venv/bin/python benchmarks/htworkload.py run --smoke          # 50 of the smaller clusters per molecule, W = 1 and 4
.venv/bin/python benchmarks/htworkload.py run --reps 3          # full workload, W = 1, 4, 8
.venv/bin/python benchmarks/htworkload.py summarize benchmarks/results/htworkload_darwin-arm64_<date>.tsv
```

`summarize` prints impl × workers → wall-clock, CPU, peak RSS, wall-clock
per alignment and the speed-up against `snake-c` at the same and at one
worker. Cells are cached under `target/htworkload/<host>/full/`, so an
interrupted run resumes; `--molecule`, `--impl`, `--workers` and
`--limit N` select subsets. On macOS wrap the run in `caffeinate -i`
(idle sleep pauses the clock and the work alike, but stretches the run).

Cost: C spends about 2 s of CPU per DNA cluster and 6 s per orthogroup
(`--auto` → L-INS-i), so one `snake-c` cell at one worker is ≈ 1.6 h
(DNA) and ≈ 2.5 h (protein); the default grid (17 cells per molecule)
is on the order of a day per replicate. `--molecule dna --reps 1` is
the primary result; add protein and replicates as time allows.

`benchmarks/results/htworkload_smoke_2026-10-31.tsv` is the pipeline
check: 50 of the smaller clusters per molecule, every path at 1 and 4
workers, one replicate, under `nice -n 19` on a machine busy with other
jobs, so its times only show that the measurements are wired up. Every
path produced all 100 alignments. C outputs agree across the Snakemake
and loop paths; Rust (CLI and pymafft) matches C on 50/50 orthogroups and
49/50 DNA clusters. The exception, `dna_01715` (three CDS of 3.6–5.0 kb,
`g01_1465`, `g02_1487`, `g11_1500`), is a genuine divergence on the FFT
path: it differs with `--retree 1` / `--retree 2` (with or without
`--maxiterate`, `--thread 1` or none) and agrees with `--nofft`,
`--localpair` and `--globalpair`. The full run reports how many more
clusters behave like it.

## Memory footprint (issue #26)

`benchmarks/memory.py` records the peak resident set size of C MAFFT
(in-tree build, through the `mafft` wrapper) and `mafft-rs` with
`/usr/bin/time -l` (macOS) or `-v` (Linux): FFT-NS-2, FFT-NS-i
(`--maxiterate 1000`), L-INS-i (`--localpair --maxiterate 1000`) and
`--parttree`, each at `--thread 1`, `4` and `8` on both sides, plus
`--memsave` (FFT-NS-2 and FFT-NS-i) on the two largest inputs, 3 runs per
cell. For C the timed process is the wrapper; the kernel's maximum RSS
covers the process and all its waited-for descendants, so the figure is
the peak of the largest engine binary (`disttbfast`, `tbfast`, `dvtditr`),
not a sum — `memory.py --verify-wrapper` shims every engine binary with
its own `/usr/bin/time` and checks that the wrapper figure equals the
per-binary maximum (it did, on the 36-sequence sample, FFT-NS-i and
L-INS-i at `--thread 1` and `4`). Peak RSS does not depend on machine
load. How to run: [`benchmarks/README.md`](benchmarks/README.md).

Inputs: the 36-sequence protein sample (median length 377), the
120 × 1.4 kb CDS DNA fixture, and the five largest BAliBASE 3 sets by
total residues (BB30003 142 seqs × 402, BB30013 86 × 672, BB30001
116 × 435, BB30005 113 × 491, BB40049 62 × 778). Apple M4 (10 cores,
32 GB), macOS 26.5, 2026-10-31; `mafft-rs` at `8bff99f` except the
`--parttree` cells, re-measured after the PartTree port of #44 (before
it, `mafft-rs --parttree` panicked on every input here above 50
sequences). Raw rows: `benchmarks/results/memory_2026-10-31.tsv` and
`memory_parttree_rust_2026-10-31.tsv`; every cell:
`benchmarks/results/memory_2026-10-31_summary.md`.

Ratio C / `mafft-rs` of the median peak RSS (> 1: `mafft-rs` uses less),
median over the 7 inputs and the range:

| Mode | `--thread 1` | `--thread 4` | `--thread 8` |
|------|-------------:|-------------:|-------------:|
| FFT-NS-2 | 2.04 (0.81–2.17) | 4.16 (2.04–6.79) | 4.78 (4.55–8.63) |
| FFT-NS-i | 1.59 (0.78–1.84) | 3.37 (2.20–5.86) | 4.74 (4.28–6.22) |
| L-INS-i | 0.51 (0.44–0.70) | 1.25 (1.18–1.99) | 2.34 (1.95–2.80) |
| `--parttree` | 0.57 (0.28–0.89) | 0.56 (0.28–0.89) | 0.55 (0.28–0.89) |
| FFT-NS-2 `--memsave` (2 inputs) | 0.56, 1.68 | 1.37, 4.31 | 2.42, 6.96 |
| FFT-NS-i `--memsave` (2 inputs) | 0.59, 1.47 | 1.35, 2.98 | 2.33, 4.64 |

Selected cells (MiB, median of 3):

| Input | Mode | C `--thread 1` | rs `--thread 1` | C `--thread 8` | rs `--thread 8` |
|-------|------|---------------:|----------------:|---------------:|----------------:|
| BB40049 (62 × 778) | FFT-NS-2 | 478 | 242 | 1,146 | 245 |
| BB40049 | FFT-NS-i | 478 | 402 | 1,822 | 402 |
| BB40049 | L-INS-i | 906 | 1,787 | 4,849 | 2,002 |
| BB30003 (142 × 402) | FFT-NS-i | 36 | 23 | 148 | 27 |
| BB30003 | L-INS-i | 50 | 86 | 185 | 95 |
| 120 × 1.4 kb CDS | FFT-NS-i | 43 | 56 | 251 | 57 |
| 120 × 1.4 kb CDS | L-INS-i | 112 | 160 | 736 | 263 |

What this shows:

- C's peak grows with `--thread N` in every mode that has a threaded
  stage (roughly 2–3× from 1 to 4 threads and again towards 8): each
  `athread` / distance worker allocates its own full-size DP and
  profile scratch. `mafft-rs` grows by a few MiB from 1 to 8 threads in
  FFT-NS-2 / FFT-NS-i (its rayon workers use pooled thread-local
  buffers and the refinement itself runs on one thread), and by 10–65 %
  in L-INS-i (the parallel all-pairs local alignment).
- Single-threaded, `mafft-rs` is lower on protein FFT-NS-2 / FFT-NS-i
  (1.2–2.2×) and higher on the DNA fixture (54–56 vs 43 MiB).
- Single-threaded L-INS-i, `mafft-rs` uses about twice C's memory on
  every input (BB40049: 1,787 vs 906 MiB). Not investigated yet; the
  likely place is the all-pairs local-alignment stage
  (`mafft-align/src/constraints.rs`), which collects every pair's result
  before building the anchor lists.
- `--parttree`: `mafft-rs` is higher on every input (the 120-sequence
  DNA fixture: 80 vs 23 MiB). Neither side uses threads here.
- `--memsave`: C's figure drops (CDS FFT-NS-2 at one thread: 43 → 30
  MiB); `mafft-rs` accepts the flag but has no Hirschberg DP yet
  (`--memsave` in the CLI reference), so its figure is unchanged and C
  is lower single-threaded on the CDS fixture.

## Multi-threading: determinism and speedup (issue #24)

`benchmarks/threads.py` runs C and `mafft-rs` at `--thread 1, 2, 4, 8,
10`, 3 runs each, interleaved (C, rs, rs, C, C, rs), and hashes every
output. `mafft-rs` must give the same bytes at every thread count, equal
to its `--thread 1` output, which is C's `--thread 1` output.

**Determinism.** Every `mafft-rs` run was byte-identical to `mafft-rs
--thread 1`, and `mafft-rs --thread 1` to C `--thread 1`, on:

- the timed inputs below (FFT-NS-i, L-INS-i, G-INS-i; 15 runs per cell);
- the five largest BAliBASE 3 sets, FFT-NS-i and L-INS-i at `--thread 1,
  4, 8`, 2 runs each (`threads_bb_largest_determinism_2026-10-31.tsv`);
- all 76 sets of BAliBASE 3 RV11, FFT-NS-i, L-INS-i and G-INS-i at
  `--thread 1, 4, 8`, 3 runs each, 2052 runs
  (`threads_rv11_determinism_2026-10-31.tsv`).

C at `--thread N ≥ 2` produced outputs different from its own
`--thread 1` in 25 of the 28 timed cells, usually 3 distinct outputs in
3 runs (exceptions: the CDS fixture at `--thread 2` and `4`, and the
sample with G-INS-i at `--thread 2`, where all 3 runs equalled
`--thread 1`).

**Speedup.** Median wall-clock of 3 runs (seconds), including process
start-up and, for C, the wrapper script. Apple M4, 2026-10-31, 1-minute
load average 2.2–5.9 (median 3.4) during the batch, which other jobs
shared; `benchmarks/results/threads_2026-10-31.tsv`.

| Input | Mode | C t1 | C t4 | C t8 | rs t1 | rs t4 | rs t8 | C speedup t8 | rs speedup t8 |
|-------|------|-----:|-----:|-----:|------:|------:|------:|-------------:|--------------:|
| sample (36 × 377) | FFT-NS-i | 0.56 | 0.29 | 0.29 | 0.39 | 0.39 | 0.40 | 1.93× | 0.97× |
| sample | L-INS-i | 1.08 | 0.46 | 0.39 | 1.08 | 0.82 | 0.76 | 2.76× | 1.43× |

| 120 × 1.4 kb CDS | FFT-NS-i | 7.93 | 5.11 | 5.01 | 5.04 | 4.94 | 4.93 | 1.58× | 1.02× |
| BB30005 (113 × 491) | FFT-NS-i | 8.77 | 4.17 | 3.02 | 7.47 | 7.43 | 7.40 | 2.91× | 1.01× |

`--thread 2` and `10` are in the TSV (10 is no faster than 8 on either
side). In `mafft-rs`, `--thread N` parallelises the distance matrices
and the all-pairs pairwise alignments of L-INS-i / G-INS-i; the
iterative refinement, which dominates FFT-NS-i and most of L-INS-i /
G-INS-i at `--maxiterate 1000`, runs on one thread, in C's `--thread 1`
branch order, so that its accept/reject decisions — and therefore the
output — do not depend on the thread count. C parallelises the
refinement too, which is where both its speedup and its run-to-run
variation come from. Single-threaded, `mafft-rs` is faster than C on
FFT-NS-i (1.2–1.6×) and slower on L-INS-i / G-INS-i on BB30005
(0.76× / 0.63×); at `--thread 8` C is up to 4.8× faster than `mafft-rs` (BB30005
G-INS-i) and level with it on the CDS fixture.
A deterministic parallel refinement (evaluating candidate branches in
parallel, then applying them in the `--thread 1` order) is the open item,
tracked in #48.

The two results are linked: at `--thread 8` C spreads the refinement over
8 workers, each with its own scratch, while `mafft-rs` runs it on one, so
the lower `--thread 8` peak RSS above is measured with `mafft-rs` doing
most of its work single-threaded. How much of that gap remains once the
refinement is parallelised is not known yet; the `--thread 1` column is
the like-for-like comparison.
